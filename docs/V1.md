# cis_bridge v1

Status: **frozen since 1.0.0**. What may change inside 1.x is in
[Frozen API](#frozen-api).

## What v1 is

cis_bridge is the one resource that knows what a server runs. It detects the
framework (ESX, QBCore, Qbox, cis_core) and the inventory, and gives every
Cisoko product one API for players, money, items, jobs and notify. A product
is written once against this API and runs on all four.

- cis_bridge depends on cis_libs only (`dependencies { 'cis_libs' }`); every
  framework, inventory and target is an optional runtime target.
- cis_core is one target among four. cis_bridge works with no cis_core. The
  adapter needs cis_core 1.x: cis_core 2.0.0 removed `CisCoreFramework()`.
- Every third-party name lives in one adapter file under `adapters/`. Nothing
  else in this repository, and nothing in a product, names one.
- v1 registers into **no** cis_libs capability slot. Products call
  `exports.cis_bridge` directly or through the facade below.

## Product API shape

Products call `exports.cis_bridge:<Name>(...)`. A thin facade exists for
readability:

```lua
-- fxmanifest.lua of a product
shared_scripts { '@cis_libs/init.lua', '@cis_bridge/init.lua' }
dependencies { 'cis_libs', 'cis_bridge' }
```

```lua
-- server
local ok, reason = CisBridge.Purchase(src, { item = 'water', count = 2, price = 10, account = 'cash' })
```

`@cis_bridge/init.lua` defines one global, `CisBridge`. Each field is a
function that forwards to the export of the same name. It holds no state and
caches nothing, so it never goes stale across a cis_bridge restart. A field
answers `false, 'no_bridge'` when cis_bridge is not started and
`false, 'error'` when the call raises across the boundary (a stopped or
restarting resource), with one console line naming the export and the
error, so a product sees the v1 result shape either way.

Every value returned across the export boundary is a msgpack copy. Results
are plain tables of strings, numbers and booleans; no function, no metatable.

## Result convention

- Success: `true` (writes) or the value (reads).
- Failure: `false, reason`. `reason` is one string from the closed list in
  [Reason codes](#reason-codes). Never `nil` first: a bare `nil` truncates the
  return list of an export.
- No contract raises. Every call into a framework or inventory runs under
  `pcall`; a raise becomes `false, 'error'` and one console line.

## Inputs every contract validates

| Input | Rule | Reason on failure |
|---|---|---|
| `src` | integer, `> 0`, and a connected player (`GetPlayerName(src) ~= nil`) | `bad_source` |
| `account` | one of `cash`, `bank`, plus `dirty` (ESX `black_money`) and `crypto` (QBCore, Qbox) where the framework has it | `bad_account` |
| `amount` | number, finite, whole, `1 <= amount <= 1000000000` | `bad_amount` |
| `item` | string, 1 to 64 chars, `^[%w_%-%.]+$` | `bad_item` |
| `count` | number, finite, whole, `1 <= count <= 1000000` | `bad_count` |
| `metadata` | `nil` or a table, at most 8 levels deep and 256 keys in total (`UseItem` data: `bad_data`) | `bad_metadata` |
| `job` | string, 1 to 64 chars, `^[%w_%-]+$` | `bad_job` |
| `grade` | number, whole, `0 <= grade <= 100` | `bad_grade` |
| `message` | string, 1 to 512 chars | `bad_message` |

The bridge validates before the framework sees anything. This matters: ESX
throws on amount ≤ 0, QBCore returns `nil`, Qbox returns `false`, and ESX
with ox_inventory lets NaN through.

## Server contracts

Realm: server. Every export below is also a `CisBridge.<Name>` facade field.

| Export | Params | Returns | Reasons |
|---|---|---|---|
| `GetPlayer` | `(src)` | `{ source, id, name, job, phone }` (`phone`: QBCore and Qbox `charinfo.phone`, nil elsewhere) | `bad_source`, `not_loaded`, `no_framework`, `error` |
| `IsLoaded` | `(src)` | boolean | never fails |
| `GetMoney` | `(src, account)` | integer | `bad_source`, `bad_account`, `not_loaded`, `no_framework`, `error` |
| `AddMoney` | `(src, account, amount, reason?)` | `true` | inputs, `not_loaded`, `refused`, `busy`, `no_framework`, `error` |
| `RemoveMoney` | `(src, account, amount, reason?)` | `true` | inputs, `insufficient_funds`, `not_loaded`, `refused`, `busy`, `no_framework`, `error` |
| `GetItemCount` | `(src, item)` | integer, never `nil` | `bad_source`, `bad_item`, `not_loaded`, `no_inventory`, `error` |
| `CanCarry` | `(src, item, count)` | `true` | inputs, `cannot_carry`, `unknown_item`, `not_loaded`, `no_inventory`, `error` |
| `AddItem` | `(src, item, count, metadata?)` | `true` | inputs, `cannot_carry`, `unknown_item`, `partial`, `refused`, `busy`, `not_loaded`, `no_inventory`, `error` |
| `RemoveItem` | `(src, item, count)` | `true` | inputs, `insufficient_items`, `partial`, `refused`, `busy`, `not_loaded`, `no_inventory`, `error` |
| `GetJob` | `(src)` | job (shape below) | `bad_source`, `not_loaded`, `no_framework`, `error` |
| `SetJob` | `(src, job, grade)` | `true` | inputs, `unknown_job`, `unknown_grade`, `refused`, `busy`, `not_loaded`, `no_framework`, `error` |
| `Notify` | `(src, message, kind?)` | `true` | `bad_source`, `bad_message`, `refused`, `no_framework`, `error` |
| `Purchase` | `(src, order)` | `true` | see [Purchase](#purchase-order) |
| `GetDoorLock` | `(id)` | `'locked'` or `'unlocked'` | `bad_door`, `unknown_door`, `unsupported`, `no_doors`, `error` |
| `SetDoorLock` | `(id, isLocked)` | `true` | `bad_door`, `unknown_door`, `unsupported`, `refused`, `no_doors`, `error` |
| `GetSummary` | `()` | `{ api, version, framework, inventory, doors, appearance, config, why }` | never fails |
| `GetOwnedVehicleId` | `(plate)` | the owned vehicle's id: Qbox `player_vehicles.id` (integer), the plate on ESX and QBCore | `bad_plate`, `not_owned`, `unsupported`, `error` |
| `SaveAppearance` | `(src)` | `true`, the save was sent | `bad_source`, `not_loaded`, `no_framework`, `no_appearance`, `unsupported`, `refused`, `error` |
| `GetGang` | `(src)` | `{ name, label, grade, isboss }` (QBCore and Qbox) | `bad_source`, `not_loaded`, `no_framework`, `unsupported`, `error` |
| `GetPlayerState` | `(src)` | `{ dead, lastStand, cuffed }`, three booleans (QBCore and Qbox) | `bad_source`, `not_loaded`, `no_framework`, `unsupported`, `error` |
| `UseItem` | `(src, item, data?)` | `true`, the item's usable callback ran | `bad_source`, `bad_item`, `bad_data`, `not_usable`, `not_loaded`, `no_framework`, `error` |
| `GetSourceByCharId` | `(charId)` | the server id of the loaded player with that character id | `bad_id`, `offline`, `no_framework`, `error` |

Player shape: `{ source:int, id:string, name:string, job:job, phone:string|nil }`. `id` is the
persistent character id: ESX `xPlayer.identifier`, QBCore and Qbox
`PlayerData.citizenid`, cis_core its own character id. `name` is the
character name, never the FiveM account name.

Job shape: `{ name, label, grade:int, gradeName, gradeLabel, isBoss:bool,
onDuty:bool, pay:int }`, normalised per framework (ESX `grade` number and `grade_salary`; QBCore `grade.level` and
`grade.payment`; Qbox `grade.level` and `job.payment`).

`kind` for notify: `info`, `success`, `warning`, `error` (default `info`). `inform`, the old ox_lib spelling, is taken as `info`.
Each adapter maps it to its framework's own type (QBCore `primary` for
`info`).

A door `id` is an integer (an ox_doorlock id) or a string of 1 to 64 chars
(a door name).

### Vehicles

`GetOwnedVehicleId(plate)` answers whether a framework stores the vehicle as
owned, and under which id. The plate is a string (a whole number is read as
its digits), trimmed of the spaces GTA pads it with, then 1 to 15 chars with
no control character; anything else is `bad_plate`.

| Framework | Lookup | Id |
|---|---|---|
| Qbox | `exports.qbx_vehicles:GetVehicleIdByPlate(plate)` | `player_vehicles.id` |
| ESX | `SELECT plate FROM owned_vehicles WHERE plate = ?` (oxmysql) | the plate |
| QBCore | `SELECT plate FROM player_vehicles WHERE plate = ?` (oxmysql) | the plate |
| cis_core | none yet | `unsupported` |

Qbox without `qbx_vehicles`, or ESX and QBCore without oxmysql, answer
`unsupported`, so a product can fall back to keying by plate instead of
treating every vehicle as not owned. A plate nobody owns is `not_owned`.

### Gang, player state and usable items

Three server exports. All three fail closed: `false, reason`,
never a bare `nil`.

`GetGang(src)` answers `{ name, label, grade, isboss }`. `grade` is the
numeric level (`PlayerData.gang.grade.level`). QBCore and Qbox store a gang
on the player; ESX and cis_core have none and answer `unsupported`.

`GetPlayerState(src)` answers `{ dead, lastStand, cuffed }` from the
metadata flags `isdead`, `inlaststand` and `ishandcuffed`. Qbox defaults
the three; on QBCore `qb-ambulancejob` and `qb-policejob` set them, so a
server without those resources reads `false` for all three. ESX and cis_core
answer `unsupported`.

`UseItem(src, item, data?)` runs the callback the framework registered for a
usable item (`QBCore.Functions.CreateUseableItem`, `ESX.RegisterUsableItem`)
for that player, as the framework's own inventory does on a click. `data` is
the optional item table handed to the callback, and must be a table (`bad_data`
otherwise). It does not check that the player holds the item and takes nothing
from them.

| Framework | Usable check | Call |
|---|---|---|
| Qbox | `exports.qbx_core:CanUseItem(item)` | the returned callback, called directly |
| QBCore | `QBCore.Functions.CanUseItem(item)` | the returned callback, called directly |
| ESX | `ESX.GetUsableItems()` | `ESX.UseItem(src, item, data)` |
| cis_core | none | `not_usable` |

Qbox has no `UseItem` export, and QBCore's `Functions.UseItem` forwards to
qb-inventory with its arguments swapped, so both call the registered callback
themselves. That skips qb-inventory's own item-used hook. ESX swallows a
callback's error inside `ESX.UseItem`, so a failing ESX callback still
answers `true`; and on an ESX core without `GetUsableItems` the bridge cannot
tell `not_usable` from usable and makes the call. A callback that raises on
QBCore or Qbox answers `error`.

### Character id to server id

`GetSourceByCharId(charId)` answers the server id of the
loaded player whose `GetPlayer().id` is `charId`, or `false, 'offline'`. A
product that stores character ids (a phone number's owner, a house's owner)
uses it to reach that player while they are online. `charId` is a string of
1 to 64 characters with no control characters (`bad_id` otherwise).

| Framework | Lookup |
|---|---|
| Qbox | `exports.qbx_core:GetPlayerByCitizenId(id).PlayerData.source` |
| QBCore | `exports['qb-core']:GetPlayerByCitizenId(id).PlayerData.source` |
| ESX | `ESX.GetPlayerIdFromIdentifier(id)`, else `ESX.GetPlayerFromIdentifier(id).source` |
| cis_core | the bridge's loaded players, each read through `GetPlayer` |

The player the lookup names is read back through the adapter, and answers
only when its character id still matches: an index entry left over from a
character switch answers `offline`. Nothing here reaches an offline
character's money or data.

### Appearance

`SaveAppearance(src)` stores the player's current look through the clothing
resource. The look lives on the client's ped, so the save has two halves:
the server half prepares what the resource needs and fires
`cis_bridge:appearance:save` to that player; the client half reads the ped
and sends the resource's own save event. `true` means the save was sent;
the resource writes it.

| Resource | Server half | Client half |
|---|---|---|
| illenium-appearance | nothing | `getPedAppearance(ped)` to `illenium-appearance:server:saveAppearance` |
| fivem-appearance | `unsupported`: it has no server side or storage | none |
| qb-clothing | asks for a reply (10 s, once), then merges the checked clothing keys into the citizen's active `playerskins` row (oxmysql `UPDATE`), keeping the face; without oxmysql `unsupported`, with no row `no_skin` | every clothing key and the hair from the ped to `cis_bridge:appearance:reply` |
| skinchanger + esx_skin | esx_skin 1.16+: asks for a reply (10 s, once), then `exports.esx_skin:SaveOutfit(src, clothes, cb)` with the checked clothing keys; older esx_skin: `exports.esx_skin:BeginSkinEdit(src)`; without esx_skin `unsupported` | 1.16+: clothing keys from the ped to `cis_bridge:appearance:reply`; older: `exports.skinchanger:GetSkin()`, clothing keys from the ped, to `esx_skin:save` |

Order: the convar `cis_bridge:appearance`, then `illenium-appearance`,
`fivem-appearance`, `qb-clothing`, `skinchanger`. qb-clothing's skin also
holds the face, its mix and the overlays, which no native reads back as it
wrote them, so the server keeps them from the stored row and changes only the
clothing keys and the hair; with no stored row it saves nothing and prints
`no_skin` in the server console, rather than write a skin with no face. A client half that fails prints its reason
in F8; the server already answered `true`.

### Money

- Whole units only. The bridge validates the amount; adapters never round.
- `RemoveMoney` reads the balance first and refuses with
  `insufficient_funds` if `balance < amount`, on every framework. This is the
  floor: QBCore bank goes to −5000 and Qbox bank is unbounded otherwise.
- **Every write is proved by reading the balance back.** The balance, not
  the framework's return value, decides:
  - moved by exactly `amount`: `true`;
  - moved by nothing: the adapter's reason, or `refused` (a framework that answers success without
    writing, such as cis_core's ESX path answering the `pcall` status, is
    caught here);
  - moved by anything else, or unreadable after the write: `error`, one
    console line and `cis_bridge:inconsistent(src, { action = 'add_money' |
    'remove_money', account, amount, moved })`. `moved` is the change seen
    in the write's own direction, or absent when the balance could not be
    read.
- `GetMoney` floors a fractional balance to an integer, and answers
  `not_loaded` when the framework gives no number, NaN or an infinity.
- Writes hold the per-player lock (below). A second write for the same player
  while one runs answers `false, 'busy'` at once; it never queues.

### Inventory

The inventory is detected separately from the framework: `cis_inventory`,
`ox_inventory`, `qs-inventory`, `codem-inventory`, `qb-inventory`, then the framework's own
(ESX base inventory). Each is one adapter file.

- `AddItem` checks `CanCarry` first on every backend (ox_inventory's
  `AddItem` has no weight check).
- `CanCarry` answers `true` when the inventory has no way to check
  (codem-inventory); the count check after the add then decides.
- `count` is required on `AddItem`, `RemoveItem` and `CanCarry`: a missing
  count is `bad_count`, never a default (qb-inventory adds 1 for a `nil`
  amount).
- **The count is the proof.** `AddItem` and `RemoveItem` read the count
  before and after.
- `AddItem` takes back a partial add: if fewer than `count` arrived
  (ox_inventory adds non-stackables partially and still returns `true`), it
  removes what did arrive. It answers `partial` when any unit could not be
  taken back, and `cannot_carry` / `refused` when nothing moved or
  everything was taken back.
- `RemoveItem` never adds back: a plain add makes fresh units without the
  serial or durability the removed ones had. A partial remove answers
  `false, 'partial'` and fires `cis_bridge:inconsistent` with the count that
  went; the export returns no count. `refused` when nothing went.
- Units that moved and could not be put back are **stuck**. They print one
  console line and fire `cis_bridge:inconsistent`. When the count cannot be
  read after a write at all, every unit is treated as stuck. Stuck units are
  capped at what this write moved: the same item arriving from elsewhere in
  the meantime is not this write's.
- `RemoveItem` reads the count first and refuses with `insufficient_items`.
- `GetItemCount` answers an integer, never `nil`. A count that is not a
  finite number (NaN, an infinity) is `not_loaded`.
- An inventory whose item lookup raises answers `error`, not
  `unknown_item`.

### Jobs

- `SetJob` checks that the job and the grade exist before it writes
  (`unknown_job`, `unknown_grade`), because QBCore's `SetJob` answers `true`
  for an unknown grade.
- The grade is an integer everywhere. The adapter converts it to the key type
  its framework uses (ESX and QBCore string keys, Qbox integer keys).
- `cis_bridge:jobChanged` fires once per change of job name or grade. On a
  framework with its own job event the bridge relays that event; on
  cis_core, which has none, the bridge fires it after its own `SetJob`.
  QBCore and Qbox re-fire their job event on login and on every duty toggle
  (`QBCore:ToggleDuty` is a client event with no cooldown), so the bridge
  remembers the last `name|grade` per player and drops a repeat. A duty
  toggle alone fires nothing: a product that cares about duty reads
  `onDuty` from `GetJob` when it acts. The memory is cleared on unload, drop
  and re-detection.

### Purchase order

`Purchase(src, order)` is the one way a product sells something. `order` is
either one line, `{ item, count?, price, metadata?, account?, reason? }`, or
a basket, `{ lines = { { item, count, price, metadata? }, ... }, account?,
reason? }` with 1 to 20 lines. `price` is the **unit** price (integer,
`0 <= price <= 1000000000`), `count` defaults to 1 and `account` to `cash`.
The total `Σ count * price` must stay `<= 1000000000` (`bad_amount`); each
factor is bounded before the multiply.

All under the per-player lock:

1. Validate every field (`bad_source`, `bad_order`, `bad_item`, `bad_count`,
   `bad_amount`, `bad_account`, `bad_metadata`).
2. `CanCarry` for every line; refuse with `cannot_carry` or `unknown_item`.
3. `RemoveMoney(src, account, total)`, proved by read-back; refuse with
   `insufficient_funds` or the adapter's reason. A total of 0 skips this step.
4. `AddItem` for each line in order, proved by count.
5. If a line failed: remove every line that landed, proved by count, then
   refund `total − Σ(stuck × price)`. On ox_inventory the take-back names
   the slots `AddItem` answered, so it never takes a copy the player already
   owned. Stuck units stay with the player and stay paid for, and fire
   `cis_bridge:inconsistent(src, { action = 'purchase', item, count })`.
   Answer the failed add's reason, or `partial` when any unit is stuck
   (a free line included). If the refund moved nothing, answer
   `refund_failed`, print one console line with source, account and amount,
   and fire `cis_bridge:refundFailed(src, account, refund)`. A refund that
   moved the wrong amount, or left the balance unreadable, may have landed:
   it answers `error` with the money `cis_bridge:inconsistent` event and
   never fires `refundFailed`, so a listener that pays `refundFailed` again
   never pays twice.

The buyer's character id is read at the start and again before step 3 and
before each line of step 4. A different character before the payment answers
`not_loaded` and moves nothing. After the payment it stops and answers
`error`: landed lines stay, nothing is taken back from or refunded to the new
character, and a refund the paying character was owed is printed and fires
`cis_bridge:inconsistent(src, { action = 'refund', account, amount, moved = 0 })`.

The product decides **what** is sold and at what price, from its own config,
and validates the request (item allowed, distance, rate limit) before it
calls `Purchase`. The bridge decides **whether** the player can pay and carry.

### The per-player lock

A token in `busy[src]`. `AddMoney`, `RemoveMoney`, `AddItem`, `RemoveItem`,
`SetJob` and `Purchase` take it; reads do not. A write that finds it held
answers `false, 'busy'`. It is released on every path, including a raise
inside the adapter (the body runs under `pcall`), and cleared on
`playerDropped`. A logout does not clear it: the source stays connected, and
a write still in flight for it must finish before the next one starts. A
late release from an old token never frees a newer lock.

Re-detection waits while any write is in flight. A framework or inventory
that stops halfway through a write leaves the write on the adapters it
started with; their calls then raise, `guard` turns that into a failure, and
the write fails closed (a Purchase keeps what landed paid for and refunds
the rest). A write re-detects before it takes the lock, so it sees an
inventory that started since the last call. "In flight" means a held lock:
a write that yields and never returns stops re-detection only until its
player drops.

The lock serialises the bridge's own writes. A third-party resource writing
the same player's money at the same moment is outside it; the read-back then
sees a balance that moved by the wrong amount and answers `error` with
`cis_bridge:inconsistent`, so the product never hands out goods on it.

## Client contracts

Realm: client.

| Export | Params | Returns | Reasons |
|---|---|---|---|
| `GetPlayerData` | `()` | `{ id, name, job }` | `not_loaded`, `no_framework`, `error` |
| `IsLoaded` | `()` | boolean | never fails |
| `Notify` | `(message, kind?)` | `true` | `bad_message`, `unsupported`, `no_framework`, `error` |
| `AddTargetZone` | `(spec)` | `true` | `bad_target`, `exists`, `no_target`, `error` |
| `AddTargetEntity` | `(spec)` | `true` | `bad_target`, `exists`, `no_target`, `error` |
| `RemoveTarget` | `(name)` | `true` | `bad_target`, `unknown_target`, `no_target`, `error` |
| `GetAppearanceComponent` | `(slot)` | `{ drawable, texture }` of the local ped | `bad_slot`, `error` |
| `ApplyClothing` | `(slot, data)` | `true` | `bad_slot`, `bad_clothing`, `error` |
| `HasBilling` | `()` | `true, name` of the billing resource | `no_billing` |
| `GetBills` | `(after?)` | `{ items = { { id, label, amount } }, more }` | `bad_cursor`, `no_billing`, `failed`, `timeout`, `error` |
| `PayBill` | `(id)` | `true`, the billing resource paid it | `bad_id`, `no_billing`, `refused`, `timeout`, `error` |

Appearance slots and what they are on the ped:

| Slot | Kind | Id |
|---|---|---|
| `hat` | prop | 0 |
| `glasses` | prop | 1 |
| `ears` | prop | 2 |
| `watch` | prop | 6 |
| `mask` | component | 1 |
| `gloves` | component | 3 |
| `pants` | component | 4 |
| `shoes` | component | 6 |
| `chain` | component | 7 |
| `top` | component | 11 |

The ped is read and dressed through the natives, whichever clothing resource
put the clothes on. A prop with nothing on reads `{ drawable = -1, texture
= 0 }`, and `ApplyClothing` with `drawable = -1` takes the prop off.
`data` is `{ drawable, texture? }`: whole numbers, drawable 0 to 4095 (a prop
also -1), texture 0 to 255 (default 0); anything else is `bad_clothing`.
`ApplyClothing` dresses the ped only; `SaveAppearance` on the server stores it.

The client data is a convenience for UI. The server re-checks everything.

Target specs:

```lua
-- zone: kind 'box' (size = vector3) or 'sphere' (size = radius)
{ name = 'shop_1', kind = 'box', coords = vec3(0, 0, 0), size = vec3(2, 2, 2),
  options = { { label = 'Open shop', icon = 'fa-solid fa-store', distance = 2.0,
                onSelect = function(entity) end,
                canInteract = function(entity) return true end } } }
-- entity
{ name = 'clerk_1', entity = ped, options = { ... } }
```

1 to 16 options, each with a 1-to-64-char `label` of its own and an `onSelect`. The
adapter translates the canonical option into ox_target's or qb-target's own
shape. `onSelect` runs on the client: a product turns it into a net event the
server validates.

- **Validation.** `bad_target` covers: an `onSelect` or `canInteract` that is
  not a function or function reference; an `icon` that is not a string of
  at most 64 characters; more than 16 options; two options with the same
  `label` (qb-target keys options by label, so the second would replace the
  first); coordinates
  that are not finite or lie outside ±10000; a size or radius that is not
  finite or not in (0, 1000); a rotation outside (-360, 360); an entity that
  does not exist. `coords` and `size` may be a real `vector3` (LuaGLM
  `type` is `'vector3'`) or a table with `x`, `y`, `z`.
- **Default distance.** An option with no `distance` gets 2.0 m on both
  ox_target and qb-target (both default to 7 m on their own). `distance`
  must be a finite number above 0 and below 50. On qb-target the zone's
  reach is the widest option, and each option keeps its own distance.
- **Names are per resource.** A name is scoped to the resource that calls
  the export (the target resource sees `<resource>:<name>`), so two
  resources may use the same name. `RemoveTarget(name)` removes only the
  caller's own target; any other name answers `unknown_target`. qb-target
  still keys entity options by label, so two products putting the same
  label on one entity collide inside qb-target.
- **Lifecycle.** When the owning resource stops, its targets are removed.
  When cis_bridge stops, every target it added is removed. When the target
  resource itself stops, the bridge forgets its records without calling
  remove; products add their targets again after it restarts.
- `GetPlayerData` and `Notify` answer `error` when the framework raises;
  `not_loaded` and `unsupported` keep their meaning.

### Billing

`HasBilling`, `GetBills` and `PayBill` list and pay the
local player's bills through the billing resource's own client callbacks.
The money moves inside that resource, under its own locks and journal; the
bridge only bounds the call and the answer. The callback runs as the calling
client, so the payer is always the local player.

| Billing resource | List | Pay |
|---|---|---|
| esx_billing 1.16.3 (on es_extended) | callback `esx_billing:getBills(after)` | callback `esx_billing:payBill(id)` |

- **Call from a thread.** The reply arrives on a later tick, so `GetBills`
  and `PayBill` wait for it (a NUI callback or `CreateThread` is a thread).
  After 10 s they answer `timeout` and ignore a later reply. A `PayBill`
  that timed out may still have been paid: read the list again.
- **Bounds.** `after` (default 0) and `id` are whole numbers, `after` 0 to
  2147483647 and `id` 1 to 2147483647 (`bad_cursor`, `bad_id`). A row whose
  `id` is out of that range, whose `amount` is not a whole number 0 to
  1000000000, or whose `label` is not a string is dropped; a label is cut to
  80 characters. A page holds at most 100 rows; `more` is true when the
  billing resource says there is a next page or the bridge cut the page.
- **Answers.** `refused` is the billing resource's own no (esx_billing gives
  no reason; not enough money is the usual one). `failed` is a list reply
  that is not a row list. esx_billing answers an empty list for a bad cursor
  and when its read limiter refuses.

| `cis_bridge:doorChanged` | server | `(id, isLocked)` |

| `cis_bridge:jobChanged` | client | `(job)` |

They are local (`TriggerEvent`); no client can fire them. The server side
listens to framework events with `AddEventHandler` only. It registers two
net events of its own, each bound to `source`: `cis_bridge:appearance:reply`
(the appearance client half answers a read) and
`cis_bridge:server:conformanceResults` (the client half of `cis_bridge test`). The client side registers the four framework client events it relays
(`esx:playerLoaded`, `esx:setJob`, `QBCore:Client:OnPlayerLoaded`,
`QBCore:Client:OnJobUpdate`) with `RegisterNetEvent`, because the framework
sends them from the server; it acts only for the detected framework. It
also registers `cis_bridge:appearance:save`, which only the server half of
`SaveAppearance` sends, and the clothing resources' net load events
(`illenium-appearance:client:reloadSkin`,
`qb-clothing:client:loadPlayerClothing`); a client firing one of these to
itself only saves or announces its own look.

## Detection

Server and client detect independently, at first use and again on
`onResourceStart` / `onResourceStop` of any candidate.

Framework order:

1. The convar `cis_bridge:framework` (`esx`, `qbcore`, `qbox`, `cis_core`)
   if set and that resource is started. A forced name that is not an adapter,
   or whose resource is not started, gives no framework and prints one line
   that says why; this holds for every forcing convar, and a wrong
   `cis_bridge:inventory` never falls back to the framework's own inventory.
   `cis_bridge:framework_resource` (and `<slot>_resource` for every slot)
   renames the forced adapter's resource; set without the forcing convar it
   gives nothing and says to set both.
2. `qbx_core` started and its probe answers.
3. `es_extended` started and `getSharedObject` present.
4. `qb-core` started, `GetCoreObject` present, and `qbx_core` **not** started
   (Qbox provides `qb-core`). A started `qbx_core` whose probe fails gives no
   framework; it never falls back to `qb-core`.
5. `cis_core` started and its `CisCoreFramework` export present.
6. None: `no_framework`.

Inventory order: the convar `cis_bridge:inventory`, then `cis_inventory`,
`ox_inventory`, `qs-inventory`, `codem-inventory`, `qb-inventory`, then the
framework's own (ESX only). `cis_inventory` ships faces under the
`ox_inventory` and `qb-inventory` names, so it is checked first.
`qs-inventory` declares `provide 'qb-inventory'`, so qb-inventory is checked
last of the five.

Doors: the convar `cis_bridge:doors`, then `ox_doorlock`, then `qb-doorlock`.
qb-doorlock has no server export to read or set a door, so its adapter
answers `unsupported` rather than fake it.

Targets (client): the convar `cis_bridge:target`, then `ox_target`, then
`qb-target`.

Billing (client): the convar `cis_bridge:billing`, then `esx_billing`
(started, with `es_extended` started and its shared object answering
`TriggerServerCallback`).

Every adapter calls exports with a colon: `exports.res:Fn(a)`. FiveM's
export proxy is `function(self, ...)` and drops its first argument
(citizenfx/fivem@46de79b `scheduler.lua:717`), so `exports.res.Fn(a)`
silently calls `Fn()`. ESX `xPlayer` and QBCore `Player.Functions` methods are
plain fields and take a dot.

## The cis_core target

`adapters/framework/cis_core.lua` is a peer adapter. It reads
`exports.cis_core:CisCoreFramework()` (a table of functions) and maps
`GetPlayer`, `GiveMoney`, `RemoveMoney`, `GetPlayerJob`, `SetPlayerJob` and
`Notify` to the contract. The bridge's own validation, balance check,
read-back and lock apply on top, as for every other framework.

- cis_core answers the `pcall` status from `GiveMoney` /
  `RemoveMoney`, not the framework's result
  (`framework/framework_server.lua:690-693`). The money read-back is what
  makes the answer true.
- cis_core fires no player or job events. The bridge seeds its loaded set
  from `GetPlayers()` and fires `cis_bridge:jobChanged` itself.
- It is picked only when no third-party framework is started (order step 5),
  or when the convar names it: on an ESX server it is a wrapper over ESX, and
  the direct adapter is one hop shorter.

## Boundary with cis_libs

- v1 registers into no cis_libs slot. `test/contract.lua` § 1b fails if any shipped
  file calls `RegisterCapability`, `UnregisterCapability`,
  `WaitCapability`, `GetCapabilities` or `Bridge.register`, or if the
  manifest loads `shared/bridge.lua` or `@cis_libs/init.lua`.
- cis_bridge no longer loads `@cis_libs/init.lua`. Its conformance suite
  (`cis_bridge test`) runs against the v1 API alone.
- `dependencies { 'cis_libs' }` stays for one reason: `shared/lib/shim.lua`
  and `server/lib.lua` (`GetLibShim`, `GetDbProxy`), an ox_lib
  compatibility surface over cis_libs callbacks and `Db*`. It is
  outside the v1 API and **deprecated in 1.0.0**:
  `GetLibShim().zones` answers `false` and a reason, because cis_libs'
  zone exports are client-only; `GetDbProxy` answers `false` and a reason.
  Both go
  in 2.0.0, and the dependency with them.
- The database and Discord slots are gone from cis_bridge. Products use the
  oxmysql API (served by oxmysql or cis_database); Discord becomes a cis_libs
  primitive.

## Frozen API

1.0.0, the first public release, freezes the v1 contract for the whole 1.x
line. A product written against it runs unchanged on every later 1.x. Each
minor appends what it adds (`node tools/check-frozen.js --append`) and never
drops or changes an entry already frozen.

| Frozen | Where it is listed | Count |
|---|---|---|
| Exports | `api.lua`, every export `stable = true` and not deprecated: name, realm and signature | 34 |
| Events | [Events](#events), by name | 7 |
| Reason codes | [Reason codes](#reason-codes) | 47 |

The snapshot is `test/frozen.json`. `npm run check:frozen`
(`tools/check-frozen.js`, in `npm run test:all` and in CI) fails when:

- a frozen export is no longer declared, moves realm, or changes signature;
- a frozen event is no longer fired by name in the shipped Lua, or leaves
  [Events](#events);
- a frozen reason code is no longer answered by the shipped Lua, or leaves
  [Reason codes](#reason-codes);
- the shipped Lua answers a code [Reason codes](#reason-codes) does not name.

Mutation rows F01-F04 (a changed signature, a dropped reason code, a
renamed event, an undocumented answered code) each fail it.

Rules for 1.x:

1. **A minor (1.1, 1.2, ...) only adds**: a new export, a new event, a new
   reason code, a new optional trailing parameter, a new adapter. A product
   that handles `false, reason` with a default branch keeps working when a
   new code appears.
2. **Nothing frozen is removed, renamed, moved realm or reordered before
   2.0.0.** An export may be marked `deprecated` in a minor, with its
   replacement named in `use`, and keeps working until 2.0.0.
3. **A patch (1.0.1, ...) changes behaviour only to match this document**,
   for example an adapter that answered the wrong reason code.
4. `test/frozen.json` is rewritten (`node tools/check-frozen.js --write`)
   only for a new major, after the break is listed in `CHANGELOG.md`.

Outside the freeze: `GetLibShim` and `GetDbProxy` (deprecated, see
[Boundary with cis_libs](#boundary-with-cis_libs)), the console output of
`cis_bridge report` and `cis_bridge test`, and every file and global that is
not an export or event above. The shape of `GetBridgeReport`,
`GetSummary` and `GetConformanceResults` results may gain fields in a
minor; a field they already return keeps its name and type.

`api = 1` in `api.lua` is the contract major and stays 1 for all of 1.x.
The product major and the contract major are both 1 today; they are counted
separately and may part.
